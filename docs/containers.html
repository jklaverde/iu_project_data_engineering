Docker Compose · iu-sensor-pipeline

Every container, what it's for, and how it's wired.

A Kaggle sensor CSV becomes a live Kafka stream, gets validated and scored by Spark, lands in Cassandra, and surfaces through a role-based web app and a Grafana KPI deck — nineteen containers, one docker compose up -d. The diagrams below are live and interactive: drag a node, scroll/pinch to zoom, click a service to see what it's directly connected to and jump straight to its detail card.

How data moves

The path a sensor reading actually takes, end to end — drawn to scale, not decoration. Teal edges carry pipeline data and animate in the direction data actually travels; grey dashed edges are read-only observation. Click any container to isolate its direct connections; click it again (or the background) to release.

data path (animated) read-only observation alert webhook (writes an in-memory buffer only) click any solid node to isolate it

  1. Replay, then invent. producer reads the Kaggle CSV top-to-bottom and publishes one JSON event per row to Kafka at a configurable rate. When the file runs out it switches instantly to a synthetic generator using the same schema, forever.

  2. Partition by device. Kafka spreads events across 3 partitions keyed by device_id, so per-device ordering holds even under concurrent processing.

  3. Validate, score, window. spark-job consumes in 30-second micro-batches: validates and enriches each event, runs rule-based + adaptive-EWMA anomaly detection, and computes 1-minute and 1-hour rollups per device and metric.

  4. Land in Cassandra. Raw events and both aggregate tables are written to the iot keyspace — the only two writers to storage in the whole stack.

  5. Backend observes, doesn't own. The FastAPI backend polls the producer's and Spark's state endpoints plus Kafka and Cassandra directly, and streams a combined snapshot to the browser over WebSocket — this is the admin role's pipeline tour.

  6. Planner reads Cassandra directly. In parallel, the same backend serves the planner role's map from Cassandra alone — latest reading + device_thresholds → status, air quality score, comfort index — independent of the WebSocket snapshot or Grafana.

  7. Metrics and logs converge on Grafana. Prometheus scrapes the exporters; promtail ships every container's stdout to Loki; Grafana renders operational KPIs from Prometheus, business KPIs straight from Cassandra, and logs from Loki — then evaluates its own alert rules against all three.

  8. Alerts loop back. When a Grafana rule fires or resolves, it POSTs to the backend's webhook. The backend keeps a short in-memory buffer and pushes the update over the same WebSocket channel; the admin UI's Alerts tab links each one straight to a scoped Grafana Explore query.

Fixes ownership on Kafka's data volume before the broker starts — and knows when not to.

Idempotent on purpose: skips the recursive chown once the directory already shows the right owner. docker compose up re-runs every one-shot init container even when scoped to unrelated services — a chown -R walking this volume while the live kafka container is actively renaming its own checkpoint files underneath it is a real race that has actually happened (ENOENT on a live .tmp file). After the first real init, this becomes a no-op forever.

Needs its own copy of the CSV and its own checkpoint mount because executors, not the driver, run applyInPandasWithState — PySpark doesn't auto-distribute pip packages to executors the way it distributes --packages JARs, so this image installs the identical pandas/pyarrow set as the driver. The driver. Three independent Structured Streaming queries, one Kafka topic, one Cassandra keyspace.

Environment (selected)

Runs three fully independent queries — raw_events (validate, flag anomalies, write every row), agg_1m and agg_1h (tumbling windows) — each with its own checkpoint directory. The Dockerfile pre-warms the Ivy cache at build time for the Kafka and Cassandra connector JARs, so no Maven download happens on every docker compose up; it also zips the spark_job package for --py-files distribution, since cloudpickle needs it importable on executors too. SPARK_JOB_MAX_OFFSETS_PER_TRIGGER exists specifically because an unbounded backlog catch-up once OOM'd an executor — it now drains gradually instead. Spark's own REST API doesn't expose Structured Streaming progress as JSON, so a custom StreamingQueryListener feeds /state.

The build context is the repo root, not ./backend like every other service — the Dockerfile needs to COPY frontend/… from a sibling directory. A hand-rolled HMAC-signed session cookie gates every route with a role claim (admin/planner) resolved from the two fixed credential pairs above — there's still no user table.

Deliberately has no healthcheck: the official image is distroless-style — no shell, no wget/curl/nc — confirmed by docker compose exec loki sh itself failing with "executable file not found." The Cassandra plugin is installed to /usr/local/grafana-plugins — deliberately outside the grafana_data volume mount. Docker only auto-populates a named volume from the image on its first creation, so baking a plugin into the default plugin path (which lives inside that volume) would be silently shadowed forever by the pre-existing, plugin-less volume. Datasources (Prometheus, Cassandra via this plugin, Loki built-in), dashboards, and alert rules (consumer lag, Cassandra write latency, elevated per-service ERROR rate, service down) all auto-provision. Alerts route to a webhook contact point that POSTs into backend's /api/admin/alerts/webhook.
