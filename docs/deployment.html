Production is a k3s host deployed with k8s/deploy.sh prod — the same script and manifests as local development (D48). Still unbuilt: TLS/ingress, multi-node, a registry ("full P6"). The old single-host Compose runbook now lives in the appendix.

Runbook

Deploy this to a public VPS.

This guide takes a fresh Linux VPS to a running, internet-reachable deployment of the stack on k3s, using the same command you use locally: k8s/deploy.sh prod up. Everything around that command — sizing, hardening, installing k3s, TLS, backups, reboots, updates — is a one-time or ongoing operator task on one specific machine, so it lives here rather than in the script. See Architecture & Containers first if you want to understand what you're deploying before you deploy it.

Scope and honesty note. This is the single-node k3s deployment that D44–D47 exercised on a real VPS. It is not the full REQUIREMENTS.md §4.1 target (three VPS, HA etcd, WireGuard, ingress with TLS) — that is still "full P6" and unbuilt (see Operations — Where to pick this up next). Concretely, today: traffic is plain HTTP (a reverse proxy in §6 is the interim fix), there is one node, images are loaded straight into k3s' containerd rather than pulled from a registry, and backups are a manual procedure (§9). The script refuses to run against a multi-node cluster instead of half-deploying to one.

What has and hasn't been run. deploy.sh's check, argument handling and config validation were exercised on the production VPS (D48). Its up, update and prod down paths reuse the logic of the live-verified local-up.sh/local-down.sh plus new prod-specific branches (below); those new branches had not yet been run end to end when this was written — treat your first prod up as the verification, and see Operations — D48 for the result once recorded.

1. Choose and size a VPS

Any provider that gives you a plain Linux VM with root/sudo access works (Contabo, Hetzner, DigitalOcean, etc.). Size the machine off REQUIREMENTS.md NFR-3:

Use casevCPURAMDisk
Demo / walkthrough only (default 100 msg/s)48 GB40 GB
Sustained 100 msg/s, running indefinitely416 GB100 GB+ (grows unboundedly — NFR-4, no data retention/TTL)
48-hour endurance run at 500 msg/s (§10)816 GB+100 GB minimum, monitor growth live

The VPS this project was verified on has 11 GiB of RAM; with the full stack plus extra Cassandra nodes its available memory dropped to a few hundred MiB and pods were OOM-killed (REQUIREMENTS.md D44/D45) — treat 16 GB as the practical floor for anything you plan to leave running.

Use Ubuntu 22.04 or 24.04 LTS (or any current Debian-family distro — the steps below assume apt). Point a DNS A record at the VPS's IP now if you plan to do the TLS step in §6; it can take a while to propagate.

2. Initial server hardening

SSH in as root (or your provider's default user) and do this before opening any application ports:

# Create a non-root sudo user (skip if your provider already gave you one)
adduser deploy
usermod -aG sudo deploy

# Copy your SSH public key to the new user, then test logging in as it
# BEFORE closing your root session, e.g.:
rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy

# Disable password auth and root login over SSH
sudo sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sudo sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config
sudo systemctl restart ssh

# Firewall: default-deny inbound, only allow SSH for now
sudo apt update && sudo apt install -y ufw fail2ban unattended-upgrades
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw enable

# Fail2ban on SSH (sane defaults are fine) and unattended security updates
sudo systemctl enable --now fail2ban
sudo dpkg-reconfigure -plow unattended-upgrades

This matches REQUIREMENTS.md NFR-11's baseline expectations (key-only SSH, default-deny firewall, fail2ban, automatic security updates), on a single host rather than the full multi-VPS hardening in that section. Note: because you'll administer k3s as root in §3–§10, you'll use sudo for the deploy.sh commands even though root SSH login is disabled.

3. Install Docker and k3s

Two separate runtimes, and it matters that they are separate: Docker only builds the project's seven custom images; k3s runs everything, using its own containerd image store. That is why docker ps is empty while the stack is running, and why deploy.sh prod up has to copy the built images across (see why it differs).

# Docker (for building images)
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker deploy
# log out and back in for the group change to take effect

# k3s (the cluster) - single node, default settings
curl -sfL https://get.k3s.io | sudo sh -
sudo k3s kubectl get nodes          # should list this host as Ready
systemctl is-enabled k3s            # should print "enabled" (starts on boot)

Gotcha (D46): the k3s installer symlinks /usr/local/bin/kubectl to the k3s binary. That bundled kubectl always defaults to /etc/rancher/k3s/k3s.yaml (readable by root only) and ignores ~/.kube/config. deploy.sh sets KUBECONFIG explicitly so it can't be fooled by this, but if you run kubectl yourself as a normal user you'll see a permission error — use sudo, or copy the file and export KUBECONFIG.

4. Get the project onto the VPS

git clone https://github.com/<your-fork-or-org>/iu_project_data_engineering.git
cd iu_project_data_engineering

The Kaggle dataset (~62 MB, public) is not committed and needs no manual fetch step — the dataset-init Job downloads it into a PersistentVolumeClaim the first time the stack starts (§7), and skips the download on later restarts. Nothing to install on the VPS for this.

5. Configure secrets and settings

Two files, two different jobs — mixing them up is the most common mistake here:

FileHoldsRead byApply changes with
.env (never committed)The four secrets + optional Kaggle credentialsdeploy.sh → Kubernetes Secret app-secretsdeploy.sh prod up, then restart pods that read a changed secret
k8s/base/config.env (committed)Every non-secret setting: rates, watermarks, BACKEND_COOKIE_SECURE, storage budget…ConfigMap app-configdeploy.sh prod up (the ConfigMap is content-hashed, so referencing pods roll on their own)
cp .env.example .env
# edit .env and set REAL values for:
#   GRAFANA_ADMIN_PASSWORD
#   BACKEND_ADMIN_PASSWORD
#   BACKEND_PLANNER_PASSWORD
#   BACKEND_SESSION_SECRET      -> generate with: openssl rand -hex 32

deploy.sh prod refuses to continue if any of those four is empty, still a changeme… placeholder, or (for the session secret) shorter than 32 characters. Locally, placeholders are allowed; on an internet-facing host a default credential is a vulnerability.

On Kubernetes, .env is read only for those secrets. Everything else in .env (host ports, PRODUCER_RATE_MSGS_PER_SEC, even BACKEND_COOKIE_SECURE) is used by docker compose alone and is silently ignored here — change those in k8s/base/config.env. deploy.sh prints a warning whenever a key exists in both files with different values. The BACKEND_COOKIE_SECURE case is the one that bites: see §6b. KAGGLE_USERNAME/KAGGLE_KEY can stay empty — the dataset is public.

6. Firewall: decide what's actually public

Under Kubernetes, only two things are published on the host — the backend and grafana Services, which are type: LoadBalancer so k3s' built-in servicelb binds host ports 8000 and 3000. Everything else (Kafka, Cassandra, Spark, Prometheus, kafka-ui, exporters) is cluster-internal — unlike the legacy Compose stack, there's nothing extra to close. k3s' own API (6443) and kubelet (10250) are open to the internet by default; the default-deny firewall from §2 is what closes them (D44).

sudo ufw allow 8000/tcp    # web app  (or skip this and only allow 443 - see 6b)
sudo ufw allow 3000/tcp    # Grafana  (or skip this too if proxying both - see 6b)
sudo ufw reload
sudo ufw status verbose    # confirm nothing else is open
Verify from a different machine. This exact rule set is what the D44 VPS ran, and the stack was reachable and 6443/10250 were closed. But ports that Kubernetes publishes itself are NAT'd by iptables rules k3s manages, which can be evaluated before ufw's normal inbound rules — so closing a published port with ufw alone has not been verified on this project's VPS. After any firewall change, test from outside: nc -vz <vps-ip> 8000 (and 3000, 6443, 10250). Don't rely on ufw status alone.

6b. Recommended: a TLS reverse proxy

Plain HTTP sends the login forms of the web app and Grafana in cleartext over the public internet. REQUIREMENTS.md NFR-11 explicitly disallows that for production, and native ingress/TLS on k3s (it ships Traefik, unused by this project) is part of unbuilt "full P6". Until then, terminate TLS in front with Caddy — automatic Let's Encrypt certificates, one file:

sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update && sudo apt install -y caddy

/etc/caddy/Caddyfile:

app.your-domain.com {
    reverse_proxy localhost:8000
}
grafana.your-domain.com {
    reverse_proxy localhost:3000
}
sudo systemctl reload caddy
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw delete allow 8000/tcp     # then VERIFY from outside that 8000/3000 are really closed
sudo ufw delete allow 3000/tcp
sudo ufw reload

If, per the warning above, 8000/3000 are still reachable from outside after removing the rules, ufw isn't governing them; the real fix is to stop publishing them on the host (change the two Services to ClusterIP and route through Traefik — the unbuilt overlay work), not more ufw rules.

Then set the cookie flag — in k8s/base/config.env, not .env:

# k8s/base/config.env
BACKEND_COOKIE_SECURE=true

and run sudo ./k8s/deploy.sh prod up. Do not set it before TLS works: with true the browser refuses to send the session cookie over plain HTTP, so nobody can log in. (A BACKEND_COOKIE_SECURE=true in .env does nothing on Kubernetes — this is exactly the mismatch deploy.sh warns about.)

7. Start the stack

sudo ./k8s/deploy.sh prod check     # read-only: k3s active? API reachable? storage class? .env sane?
sudo ./k8s/deploy.sh prod up

check changes nothing — run it whenever something seems off. up is idempotent and safe to re-run. It builds the seven custom images, loads them into k3s' containerd, stages k8s/base/generated/ from infra/, creates the namespace, generates app-secrets from .env, runs kubectl apply -k k8s/base, then waits and prints a verdict. First start takes several minutes (Spark dependency pre-warm, Kaggle download). Watch it:

sudo ./k8s/deploy.sh prod status
sudo kubectl -n iot-pipeline get pods -w

Long-running pods should reach Running; the three one-shot Jobs (dataset-init, kafka-topic-init, cassandra-schema-init) should show Completed — that's success, not a crash. A restart or two of backend, kafka-exporter or spark-job while the stack is starting is expected: they can start before their dependencies are ready and recover by themselves (init-wait loops plus normal restart backoff). A pod that keeps restarting after several minutes is not. Then open http://<vps-ip>:8000 (or your TLS hostname) and log in as the admin or planner.

Want to run each step yourself? The README's "What deploy.sh up does, step by step" lists the raw docker build / k3s ctr images import / kubectl commands, in order, for both environments.

8. Make sure it survives a reboot

systemctl is-enabled k3s     # must print "enabled"  (deploy.sh check verifies this)
systemctl is-enabled docker  # only needed for building; harmless either way

k3s starts on boot and Kubernetes recreates every pod, so the stack returns on its own (REQUIREMENTS.md NFR-8). Persistent data survives because it lives on the host disk under /var/lib/rancher/k3s/storage, not in the pods.

One trap: the manifests reference images tagged :local that exist only in this host's k3s containerd — there's no registry to pull them from. If those images are ever removed, a recreated pod fails with ErrImagePull. Two things do that: k3s crictl rmi --prune, and kubelet's automatic image garbage collection once the disk passes ~85% full. Keep the disk well below that, and if it happens, just re-run sudo ./k8s/deploy.sh prod up — it rebuilds and reloads every image. (docker system prune is safe for this: Docker's store is separate from k3s'.)

9. Backups

All state lives in PersistentVolumeClaims backed by local-path directories on this host. Deleting the namespace (deploy.sh prod down) destroys them, and nothing replicates them (single node) — so a backup that never leaves the VPS isn't a backup. Only the Cassandra data is worth backing up for real: it's the sensor history. Kafka data and Spark checkpoints are consumer state, and the Kaggle dataset is re-fetched automatically. Grafana and Prometheus data are optional.

# The directories are named pvc-<uid>_iot-pipeline_<claim>; confirm with:
sudo ls /var/lib/rancher/k3s/storage

# 1. Stop the only writer to Cassandra (Kafka retains the backlog; spark-job catches up
#    from its checkpoint afterwards)
sudo kubectl -n iot-pipeline scale deployment spark-job --replicas=0
# 2. Flush memtables to disk on every Cassandra pod (adjust for the pods that exist)
sudo kubectl -n iot-pipeline exec cassandra-0 -- nodetool flush
# 3. Archive the Cassandra (and optionally Grafana/Prometheus) volumes
cd /var/lib/rancher/k3s/storage
sudo tar czf ~/backup-$(date +%F).tar.gz $(ls | grep -E '_iot-pipeline_(data-cassandra-|grafana-data|prometheus-data)')
# 4. Resume
sudo kubectl -n iot-pipeline scale deployment spark-job --replicas=1

Copy the archive off the VPS (scp/rsync, or your provider's whole-disk snapshot). Caveats: this is a flushed, writers-stopped copy of a live Cassandra — good enough for a demo-grade deployment, not a substitute for nodetool snapshot-based backups on anything critical. The restore procedure (stop the Cassandra pods, place the directories into the new volumes) has not been rehearsed on this project — do a test restore before you rely on it.

10. Updating

cd iu_project_data_engineering
git pull
sudo ./k8s/deploy.sh prod check

Then apply what changed. These are different commands on purpose — images are tagged :local, and re-loading an image under the same tag isn't a change Kubernetes can see in the pod spec, so up alone would leave the old container running:

What changedRun
backend/ (incl. the frontend it bundles)sudo ./k8s/deploy.sh prod update backend
producer/… update producer
spark_job/ (both images are built from it)… update spark-job spark-worker
infra/cassandra/ (restarts the database, one pod at a time)… update cassandra
infra/grafana/… update grafana
k8s/base/*.yaml, k8s/base/config.env, or infra/ config (Prometheus/Loki/Grafana provisioning)sudo ./k8s/deploy.sh prod up (settings roll their pods automatically)
A secret in .env… up, then kubectl -n iot-pipeline rollout restart deployment/<name> for pods that read it (a changed Secret doesn't roll pods)

If up fails with a Job field being immutable, delete that Job (kubectl -n iot-pipeline delete job <name>) and re-run up — the init Jobs are idempotent. If a pip-compiled requirements.txt changed, --require-hashes still applies at build time (see Architecture & Containers' supply-chain notes). Never repeat the full down/up cycle for a code change — it deletes the data.

11. Monitoring, logs, and troubleshooting

sudo ./k8s/deploy.sh prod status                       # pods, PVCs, Services
sudo kubectl -n iot-pipeline get pods                  # health at a glance
sudo kubectl -n iot-pipeline logs -f deploy/backend    # tail one service
sudo kubectl -n iot-pipeline logs statefulset/kafka --since=1h
sudo kubectl -n iot-pipeline describe pod <name>       # why is it Pending / CrashLoopBackOff?
sudo kubectl top nodes                                 # headroom (metrics-server ships with k3s)

Grafana's dashboards (KPI-1 through KPI-5) are the primary operational view once running — see REQUIREMENTS.md §9 — and the admin role's Kubernetes tab shows the same pod health inside the web app, with centralized logs available alongside it. For anything that looks wrong at the infrastructure level, check Operations — Troubleshooting first.

12. Tearing down

sudo ./k8s/deploy.sh prod down          # lists the PVCs to be destroyed, asks you to type the namespace
sudo ./k8s/deploy.sh prod down --yes    # same, non-interactive (scripts only)

This deletes the iot-pipeline namespace and, with it, every PVC and all its data — irreversible. It deliberately leaves k3s itself (and its system pods, Traefik, the storage provisioner) running, so a later up starts from a healthy cluster. Verify the volumes are gone with du -sh /var/lib/rancher/k3s/storage. Optional cleanup it does not do: the loaded images (k3s crictl rmi …) and Docker's build cache (docker system prune -a).

To remove everything, including k3s and every namespace on it: sudo /usr/local/bin/k3s-uninstall.sh — this is the cluster, not the project, so it is intentionally not part of deploy.sh.

Local vs production: what differs, and why

Both environments run k8s/deploy.sh against the same manifests (k8s/base) with the same steps: build images → load them into the cluster → stage generated/ config → namespace → Secret from .env → kubectl apply -k → wait. Manifests, the Secret flow, config.env, image tags, RBAC and readiness checks are identical. Only what has to differ does (each is a commented branch in the script):

AspectLocalProductionWhy it differs
Who owns the clusterCreates it on up, deletes it on downNever creates or deletes k3s; manages only the iot-pipeline namespaceA dev cluster is disposable and a clean slate is the point. The prod cluster is long-lived host infrastructure (installed once, possibly running other workloads); a project script must not be able to remove it.
Kubernetes flavork3d (k3s in Docker containers)Native k3s (systemd service)Same k3s distribution (D43), so manifests behave the same. k3d needs only Docker and is throwaway; on a server, native k3s avoids Docker-in-Docker and has its own lifecycle (D18).
How images get ink3d image importdocker save … | k3s ctr images import -Different image stores: k3d nodes are containers with their own; native k3s has its own containerd, separate from Docker's. No registry exists yet.
Which kubeconfigk3d kubeconfig write/etc/rancher/k3s/k3s.yaml (PROD_KUBECONFIG to override)Explicit in both, never ambient (the D46 bug): a k3s host's kubectl silently ignores ~/.kube/config, which would aim a "local" deploy at production or vice versa.
How ports reach the host-p 8000:8000@loadbalancer at cluster creationservicelb binds host 8000/3000; ufw gates themSame LoadBalancer Services in both. k3d's "node" is a container, so its ports must be mapped up front; native k3s binds directly on the host.

Not in deploy.sh—Host hardening, installing k3s, TLS, backups, reboot survivalOne-time or ongoing operator tasks on a specific machine — not part of a repeatable app deploy. Documented in this runbook instead.

Known gaps, not intentional differences: no TLS/ingress (plain HTTP), single node, no image registry, manual backups. These are unbuilt work (REQUIREMENTS.md §4.1 / D48), and deploy.sh is structured so a production Kustomize overlay can add them without changing how you run it.

Appendix: legacy docker compose

Before D43 this project deployed to a VPS with docker compose, and that is what this guide used to describe. It still works, but it is no longer the production path, and it differs in ways that matter:

  • The admin's Cassandra node-deploy and Kubernetes-status tabs return 503 — they need the Kubernetes API.
  • It reads all its settings from .env (unlike Kubernetes, where non-secret settings live in k8s/base/config.env).
  • Volumes are named Docker volumes; docker compose down -v deletes them.
Security: the firewall does not protect Compose's ports. docker-compose.yml publishes every service on all interfaces — Kafka (9092), Cassandra (9042, 7070), Spark (7077, 8090, 8091, 4040), the producer/spark-job state ports (8001, 8002), Prometheus (9090), Loki (3100), the exporters (9308, 9100) and kafka-ui (8080), besides the app on 8000 and Grafana on 3000. Docker writes its own iptables rules, which are evaluated before ufw, so ufw default deny incoming and ufw allow 8000 do not keep those other ports off the internet. (An earlier version of this guide claimed ufw allow rules "close that gap" — they don't; that was wrong.) Before running Compose on a public host, either bind the internal ports to loopback in docker-compose.yml ("127.0.0.1:9092:9092" instead of "9092:9092", for every port except the app and Grafana) or add rules to Docker's DOCKER-USER chain — then verify with a port scan from another machine. Comment out kafka-ui entirely if you don't need it. 
docker compose up -d --build --wait     # up (needs Docker + the compose plugin; no k3s)
docker compose ps                       # every long-running service healthy; *-init = Exited (0)
docker compose logs -f backend          # logs
git pull && docker compose up -d --build   # update (recreates only what changed)
docker compose down                     # stop, keep volumes
docker compose down -v                  # stop AND delete all data - irreversible

Sizing (§1), server hardening (§2) and the Caddy TLS proxy (§6b, pointing at localhost:8000/3000) apply unchanged. Every long-running service has restart: unless-stopped, so the stack returns after a reboot as long as the Docker service is enabled (systemctl is-enabled docker). Backups are the named volumes: docker compose stop, then tar the iu-sensor-pipeline_cassandra_data (and optionally grafana_data/prometheus_data) directories under /var/lib/docker/volumes, then docker compose start.
