Resuming locally

docker compose up -d --wait

Brings up the full stack — the producer starts automatically and immediately begins replaying the Kaggle dataset at 100 msg/s into topic sensor-readings, and the Spark job starts consuming and writing to Cassandra right after. Grafana auto-provisions both datasources and the KPI dashboard with zero manual steps. See the root README.md for the verification checklist.

Always use this bare, whole-project form (no service name) to resume/reconcile — a scoped docker compose up -d --build <service> only touches that one service and leaves any sibling that had drifted to Exited (host sleep, a Docker Desktop restart, a crash loop) dead until something names it again (P9).

If you edit infra/prometheus/prometheus.yml while the stack is already running, docker compose restart prometheus is required — it does not hot-reload scrape config from a running container.

Heads up on cold start: on first launch (or after a full down -v), the Spark job recomputes its anomaly-detection baseline from the CSV (~30–60s) before it starts consuming, and if Kafka already has a large backlog, the first micro-batch can take several minutes to catch up — expected, not a hang (see P3).

The Kaggle dataset is fetched automatically by the dataset-init one-shot service into a named volume — no manual step, and a no-op on restarts once the volume has the file (see P6 for the bug this replaced). To fetch it by hand instead, run python kaggle_repository/download_repository.py.

Implementation decisions beyond the spec

REQUIREMENTS.md is frozen and deliberately doesn't cover implementation details. These were decided while building and matter for anything downstream that touches the same surfaces.

Kafka / Cassandra (P1)

  • Compose project is named iu-sensor-pipeline and no service sets an explicit container_name: — namespaces every container to avoid clashing with unrelated Docker projects on a shared dev machine (P1 §3).
  • Kafka's actual KRaft log directory had to be pinned via KAFKA_LOG_DIRS to match the mounted volume (P1 §2) — do not drop that env var without re-verifying persistence across a real down && up -d cycle.
  • raw_events is partitioned by (device_id, bucket_start) where bucket_start is a 15-minute bucket, sized for the NFR-2 endurance rate. agg_1m / agg_1h are partitioned by (device_id, day) / (device_id, month).
  • The raw_events table has a few columns beyond the literal §5.2 field list: write_ts (Spark sink write time, feeds KPI-2), is_synthetic, is_anomaly, anomaly_reason. The producer only ever populates is_synthetic — the rest are Spark-job-owned.
  • Grafana gets no default credential — GF_SECURITY_ADMIN_PASSWORD is required with no fallback.

Producer (P2) — the wire contract P3 must consume

  • Kafka message value is JSON with exactly: event_id, device_id, event_ts, ingest_ts, co, humidity, lpg, smoke, temp, light, motion, pressure, is_synthetic. No is_anomaly/anomaly_reason/write_ts/bucket_start — those are Spark/Cassandra-sink-owned.
  • event_ts/ingest_ts are ISO-8601 UTC strings with millisecond precision, e.g. "2026-08-18T10:00:00.000Z" — not epoch millis, so Spark's to_timestamp() parses natively.
  • Kafka message key = device_id (UTF-8) — matches FR-K1's partitioning intent.
  • The producer runs always-on with plain docker compose up -d (no profiles: gating) — every restart re-starts ingestion from the beginning of the CSV unless PRODUCER_REPLAY_ROW_LIMIT is set.
  • Producer state is exposed at GET http://localhost:${PRODUCER_STATE_PORT}/state — read-only telemetry (FR-I4), not a control surface. UC-7 (UI control panel) remains an explicitly later phase.
  • Anomaly injection (synthetic mode only) can spike multiple metrics per event simultaneously (weighted 1/2/3 metrics: 70/25/5%), each offset by PRODUCER_ANOMALY_SIGMA_MULTIPLIER (default 4.0, deliberately above §5.4's 3σ threshold to survive baseline drift). P3's detector expects this.

Spark job (P3)

  • Anomaly detection uses an adaptive EWMA per (device, metric) — not a static one-time baseline — seeded from a batch read of the CSV at startup, then continuously updated (decay SPARK_JOB_ANOMALY_EWMA_ALPHA, default 0.001, ≈ 2000-event/12–60s effective window). Checked before updating with the current event's own value.
  • A separate static per-device absolute ceiling exists for co/smoke/lpg only (max(observed_max, p999) × 1.5). temp/humidity rely on the sigma rule alone.
  • anomaly_reason is a semicolon-joined metric:kind(detail) string and can reflect multiple simultaneously-triggering metrics on one event. Confirmed working for both real historical-data outliers during replay and injected synthetic anomalies.
  • Three fully independent Structured Streaming queries (raw_events, agg_1m, agg_1h), each with its own Kafka read and own checkpoint (state-store data is written by executors — P3 §5).
  • write_ts exists only on raw_events — do not add it to agg_1m/agg_1h writes, their schemas don't have that column (P3 §8).
  • FR-S4: same pattern as the producer — a stdlib HTTP /state endpoint fed by a custom StreamingQueryListener (Spark's own REST API on :4040 doesn't expose Structured Streaming query progress).
  • spark-worker builds a custom image instead of pulling apache/spark:3.5.9 directly, and mounts both the dataset and checkpoint volumes — required because executors run there, not the driver (P3, entirely about this driver/executor distinction).

Observability (P4) — wire contract for P5

  • Producer and Spark job both gained GET /metrics (hand-formatted Prometheus text, no prometheus_client dependency) alongside /state — same port, same HTTP server.
  • KPI-1 lag is genuinely 3 separate numbers — the three queries are independent Kafka consumers (Structured Streaming doesn't use classic consumer-group offsets); lag is broker offset minus Spark's self-reported offset, by query — don't collapse to one number.
  • KPI-2 latency is a per-micro-batch snapshot (p50/p95/max of write_ts − event_ts, plus a hop breakdown), computed only where all 3 timestamps exist on one row (raw_events). Refreshed every trigger interval, not a true cross-batch streaming quantile.
  • Grafana needs two datasources — Prometheus (KPI-1/2/4) and a baked-in Cassandra plugin (KPI-3/5), installed at a path outside the pre-existing grafana_data volume (would otherwise be silently shadowed forever).
  • Cassandra builds a custom image too, baking in a jmx_exporter javaagent. The exporter config is fetched verbatim from jmx_exporter's own official example — if KPI-4 metrics ever need to change, re-diff against upstream rather than guessing MBean names (P4 §12).
  • The dashboard's $device_id variable is a static list (the 3 real device MAC IDs), not CQL-driven — SELECT DISTINCT isn't valid on a partial partition-key column in Cassandra.

Web app (P5)

  • One combined container. backend's Dockerfile is multi-stage: a Node stage builds React, a Python stage serves the built dist/ via StaticFiles at /, alongside /api/* and /ws/*.
  • Auth: two fixed credential pairs (admin/planner, both required env vars, no defaults) plus a hand-rolled HMAC-SHA256-signed session cookie — no session-management dependency, deliberately, since there's no user table.
  • Live updates: WebSocket is primary; the frontend falls back to polling if the socket doesn't open within 3s or drops. The backend's own background loops poll regardless of which transport reaches the browser.
  • Upstream-outage resilience: the state poller caches the last-known-good producer/spark-job state and merges fresh data on top of that cache rather than {} — a transient restart no longer changes the response shape. Added after a real crash was found live (P5 §2) — do not remove this caching without re-verifying survival of a mid-session restart producer.
  • Cassandra "recent rows" bucket selection is event-time-based, not wall-clock — derives which partitions to point-read from real timestamps sampled off Kafka, required because REPLAY-mode event_ts used to be historical (P5 §1).
  • No Docker socket is used for the deployment-status step — every service is probed over its own HTTP/TCP port instead.
  • Known, accepted limitation: /api/anomalies can hit READ_TOO_MANY_TOMBSTONES under high data volume, shared with the P4 Grafana panel it mirrors (P5 §3).

Interim VPS deployment

Not the full REQUIREMENTS.md §4.1 target (3-VPS k3s — that's "full P6," not started). This is smaller, real work: making the existing single-host Compose stack actually deployable on a public VPS — and it has genuinely been deployed to and exercised on a real Linux VPS (dataset fetch tested cold, Grafana login reconfigured, a real dashboard bug found and fixed against the live instance).

  • dataset-init — a one-shot service, same idiom as kafka-topic-init/cassandra-schema-init, downloads the Kaggle dataset into a named volume before producer/spark-job/spark-worker start. Replaces a manual host-side step that was easy to forget and failed outright on modern Debian/Ubuntu (PEP 668). Confirmed needs no Kaggle credentials. Full story: P6 §1.
  • Every long-running service got restart: unless-stopped — without this, an unattended VPS reboot leaves most of the stack down.
  • This documentation site is new — the "how it's built" and "how to deploy it" docs are written to be read by a newcomer, not just future-Claude.
  • A real bug was found and fixed against the live VPS deployment: four KPI-5 Grafana panels used bare $granularity in a table-name position instead of ${granularity}. Full story: P4 §14.
  • The live VPS deployment's IP/credentials are intentionally not recorded anywhere in this repo.

What full P6 (k3s) needs to know

  • The whole web app is one container — P6's k3s manifests need exactly one Deployment/Service for it, not two. No Docker socket dependency to port.
  • BACKEND_ADMIN_PASSWORD and BACKEND_SESSION_SECRET are required env vars with no defaults — P6's secrets management needs to supply both. BACKEND_COOKIE_SECURE=false is local-dev-only; P6 must set it true.
  • All three Python services' lockfiles are hash-pinned and installed with --require-hashes — regenerate via pip-compile --generate-hashes (see backend/README.md), don't hand-edit.

Troubleshooting log

Non-obvious bugs, gotchas, and environment quirks — ordered by phase. Kept so a future debugging session doesn't rediscover the same root cause from scratch.

P1 — Foundation (local docker-compose stack)

3 incidents
#1 Cassandra crash-loops on boot: unable to find snitch class
Symptom

cassandra exits immediately (exit code 3) on every start; docker compose logs cassandra shows ConfigurationException: Unable to find snitch class 'org.apache.cassandra.locator.GossipPropertyFileSnitch'.

Cause

Typo. The real class is GossipingPropertyFileSnitch (with "-ing") — there is no GossipPropertyFileSnitch in Cassandra.

Fix

CASSANDRA_ENDPOINT_SNITCH: GossipingPropertyFileSnitch in docker-compose.yml.

#2 Kafka data silently does not survive a restart (breaks NFR-8)
Symptom

No error at all — the stack looks healthy after every restart. But the topic's TopicId is different every time, meaning the whole KRaft cluster was silently recreated from scratch.

Cause

The volume was mounted at /var/lib/kafka/kafka_data, but the apache/kafka:3.7.0 image's actual KRaft log directory is /tmp/kafka-logs — visible only in the JVM's own runtime log line, not in the config file that looks effective but is just a template. The mounted volume was therefore never actually written to.

How it was found

Inserted a probe row / recorded a TopicId, ran a real down + up -d cycle, and diffed before/after — config validation alone does not catch this class of bug.

Fix

Two parts: (1) KAFKA_LOG_DIRS: /var/lib/kafka/kafka_data explicitly set. (2) A new one-shot kafka-volume-init service (runs as root, chowns the volume) that kafka depends on via service_completed_successfully — needed because a fresh named volume mounts root-owned by default, but the image runs as non-root uid 1000.

General lesson

Don't trust a config file found via find/cat inside an image to be the effective runtime config — confirm the actual data directory from the process's own startup log, and confirm persistence by actually cycling the stack and diffing an identifier, not just checking the container starts.

#3 Host port / container-name collisions are with unrelated things on this machine
Symptom & cause

kafka-ui's default host port 8080 collided with an unrelated pre-existing process on this dev machine — worked around by remapping KAFKA_UI_PORT in the local, gitignored .env (deliberately not changed in .env.example). Separately, stopped leftover containers already existed named kafka/kafka-ui/spark-master from unrelated old projects.

Fix

Fixed at the project level, not by touching those containers: added name: iu-sensor-pipeline at the top of docker-compose.yml and removed every explicit container_name: override, so Compose namespaces everything as iu-sensor-pipeline-<service>-1.

General lesson

Don't hardcode container_name: in a compose file meant to run on a shared dev machine — let Compose's project-prefixed default naming do its job.

P3 — Processing (PySpark Structured Streaming job)

5 incidents

The unifying theme of every bug below: this is a real distributed cluster (a spark-job driver container plus a separate spark-worker executor container), not a single-process local Spark session. Anything that "obviously" only needs to exist on the driver can silently fail on the executor instead. Every fix is a variant of "make sure executors have it too, not just the driver."

#4 Batch CSV read fails on the executor: file does not exist
Symptom

The job's one-time baseline-seed read fails with SparkFileNotFoundException, reported by a task running on the worker's IP, not the driver.

Cause

spark.read.csv(...) is a distributed batch read — Spark schedules the actual read task on an executor, not the driver. Only spark-job's compose service had the volume mounted.

Fix

Mount the same volume into spark-worker too.

General lesson

Any local file path a Spark job reads or writes must be mounted identically on every node that can run a task for that job, not just the driver — true even for a single-worker "cluster."

#5 Checkpoint mkdir fails for state-store paths
Symptom

java.io.IOException: mkdir of file:/opt/spark-checkpoints/agg_1m/state/1/0/_metadata failed.

Cause

Two layered issues: a fresh named volume mounts root-owned (same lesson as P1 §2), fixed with a spark-job-volume-init one-shot chown -R 185:185. Less obviously: Structured Streaming's state-store data (for applyInPandasWithState and windowed aggregations) is written by executors, not the driver — so spark_checkpoints also needed mounting into spark-worker.

Fix

Mount spark_checkpoints into both spark-job and spark-worker; chown via spark-job-volume-init before either starts.

#6 ModuleNotFoundError: pandas / pyarrow on the executor
Symptom

The driver starts fine, but the first micro-batch that runs applyInPandasWithState fails on the executor with ModuleNotFoundError, deep in PySpark's Arrow serialization code.

Cause

applyInPandasWithState is a pandas UDF under the hood — needs pandas/pyarrow wherever it actually executes, which is the executor. The base apache/spark:3.5.9 image ships neither; spark_job/Dockerfile correctly installs both, but spark-worker was still using the plain upstream image.

Fix

A new spark_job/worker.Dockerfile (base image + the same requirements.txt), and spark-worker switched from a pulled image: to a build: using it.

General lesson

PySpark auto-distributes --packages JARs to executors, but does not auto-distribute pip-installed Python packages — those need to be baked into whatever image the executors actually run.

#7 ModuleNotFoundError: spark_job, unpickling a closure
Symptom

Different from #6 — this is the job's own package failing to import on the executor while deserializing the applyInPandasWithState function via cloudpickle.loads.

Cause

A wrong assumption: cloudpickle pickles functions defined in an importable module (as opposed to __main__) by reference, not fully "by value" — it expects the receiving side to import it. Since spark_job was never shipped to the executor, unpickling fails there.

Fix

Zip the spark_job/ package at build time and add --py-files /opt/app/spark_job.zip to the spark-submit command.

General lesson

Don't assume PySpark UDF closures are executor-independent just because they're passed as plain Python callables — if the function lives in a real package, ship it via --py-files regardless.

#8 Cassandra connector rejects a write with columns the table doesn't have
Symptom

NoSuchElementException: Columns not found in table iot.agg_1h: write_ts — the connector aborts outright rather than silently dropping the column.

Cause

The shared foreachBatch writer helper unconditionally added a write_ts column to every DataFrame, but only raw_events actually has that column — a window's aggregate has no single meaningful "row write time."

Fix

Made stamp_write_ts a parameter of the writer factory, True only for the raw_events query.

General lesson

A generic "one writer for every table" helper is a trap the moment the tables' schemas actually differ — verify against each target table's real column list.

General P3 lesson: all five bugs above were caught by actually running the job against the live stack — including a stack that already had ~9 hours of real producer traffic queued in Kafka. None would have surfaced from a syntax check or code review alone — they're all specifically about the driver/executor split in a genuine (if small) cluster.

P4 — Observability (Prometheus exporters, Grafana dashboards)

6 incidents
#9 node-exporter's recommended rslave mount fails on Docker Desktop
Symptom

docker compose up fails immediately: path / is mounted on / but it is not a shared or slave mount.

Cause

rslave mount propagation needs the source mount to already be a shared/slave mount — not guaranteed by Docker Desktop's Linux VM on Windows.

Fix

Drop the propagation flag, mount as plain /:/host:ro.

#10 Cassandra's base image can't download over HTTPS at build time
Symptom

RUN curl -fsSL ... jmx_prometheus_javaagent.jar fails during docker build with error setting certificate file, even after installing curl.

Cause

The base image has neither curl nor ca-certificates. curl alone isn't enough for HTTPS — without a CA bundle it can't verify any TLS certificate.

Fix

apt-get install -y curl ca-certificates together.

#11 Modern Grafana images don't have grafana-cli
Symptom

grafana-cli: not found.

Cause

Grafana consolidated its CLI into the main binary — it's grafana cli ... (a subcommand), not a separate executable. Confirmed by running grafana --help inside the image.

Fix

grafana cli --pluginsDir "$DIR" plugins install <id> <version> — --pluginsDir is a flag on cli itself, before the subcommand.

Related gotcha, same step

The image's grafana user has no matching grafana group — its actual group is root (gid 0). Use chown -R grafana:root, not grafana:grafana.

#12 jmx_exporter: actual metric names differ from assumption
Symptom

Dashboard panels for disk usage and GC pauses show no data even though the exporter is scraping fine.

Cause, two issues

(1) The Storage/Load MBean exposes its value via a Count attribute in this Cassandra version, not Value — producing cassandra_storage_load_count, not the assumed cassandra_storage_load. (2) jmx_exporter's javaagent auto-exports jvm_gc_collection_seconds_{count,sum} from its own built-in JVM collector, independent of the custom rules config — a custom GC rule was silently never used.

How it was found

Curling the exporter's raw /metrics output directly and grepping for the expected names, rather than trusting the dashboard JSON was correct because the config "looked right."

Fix

Dashboard queries updated to cassandra_storage_load_count and jvm_gc_collection_seconds_sum (unit s, not ms); the redundant custom GC rule deleted entirely.

General lesson

Don't trust an exporter config's intended metric names without checking the exporter's actual /metrics output.

#13 CQL clause order: LIMIT before ALLOW FILTERING
Symptom

A Grafana panel query fails with mismatched input 'LIMIT' expecting EOF when the query ends in ... ALLOW FILTERING LIMIT 100.

Cause

CQL requires LIMIT to appear before ALLOW FILTERING — the reverse of what reads naturally in English.

How it was found

Testing the dashboard's exact query strings directly against Grafana's /api/ds/query endpoint with real parameters, not just visually reviewing the JSON.

Fix

... LIMIT 100 ALLOW FILTERING.

General lesson

For any datasource where the "query" is an opaque string inside dashboard JSON, verify it by actually executing it through the real API before trusting it provisions cleanly.

#14 KPI-5 panels fail: bare $granularity isn't interpolated in a table-name position
Symptom

All four KPI-5 panels error with a CQL parser complaint pointing right after a $ character.

Cause

The panel queries used bare $granularity in the FROM clause, while a working variable elsewhere in the same queries used the curly-brace form. The bare form was never substituted — Cassandra's CQL grammar treats a bare $ as the start of a dollar-quoted string literal.

How it was found

Reproduced the exact error directly against the real Cassandra container via cqlsh, using the literal unsubstituted query text — then confirmed the fix works with a real value substituted in.

Fix

FROM iot.${granularity} WHERE ... in all four KPI-5 panel queries.

Update (D28) — root cause since fixed, kept for history

The "No data during REPLAY" behavior this note originally also covered no longer happens — the producer now stamps event_ts = now() at publish time (same as synthetic mode), so window_start tracks real wall-clock time throughout REPLAY mode too. Same root cause as P5 §1, just surfacing in a Grafana panel instead of the web app's backend.

General lesson

Don't assume Grafana's bare $var and ${var} interpolation are interchangeable in every position — prefer ${var} everywhere for raw-query datasources to remove the ambiguity entirely.

General P4 lesson: every finding above was caught by reading an official upstream example/tool's output directly, or actually executing the exact query/command a dashboard or Dockerfile would run, rather than treating "the config looks right" as sufficient.

P5 — Web app (FastAPI backend + React frontend)

3 incidents
#1 "Recent Cassandra rows" returns nothing during REPLAY mode
Update (D28)

Root cause now fixed at the producer (event_ts = now(), see P4 §14). The workaround below is no longer strictly necessary but is harmless and hasn't been ripped out.

Symptom

The Cassandra step's "recent rows" panel showed old/unrelated rows (or none) for most of a fresh session, only correct once the producer handed over to synthetic generation.

Cause

raw_events' partition key is (device_id, bucket_start), derived from each row's own event_ts — NOT wall-clock time. During REPLAY, that was a historical Kaggle date, so a query guessing "the current bucket" from datetime.now() queried buckets replay rows never land in.

How it was found

Watching the live UI show a fixed set of rows with a stale write_ts, then cross-checking real event/bucket timestamps against what the Cassandra step was querying for.

Fix

recent_raw_events_sync now takes reference_timestamps sampled from real Kafka messages and derives buckets from those, falling back to wall-clock only on cold start.

#2 One transient upstream hiccup crashed the entire frontend
Symptom

Restarting producer mid-session sometimes left the whole web app frozen on "Loading..." requiring a manual reload. Console: TypeError: Cannot read properties of undefined (reading 'toLocaleString').

Cause

state_poller.py spread producer_state directly into the response; when the poll failed, it was None, silently dropping fields — and IngestionStep.tsx called .toLocaleString() unconditionally. React 18 unmounts the entire root on an uncaught render error with no ErrorBoundary in place.

How it was found

Actually restarting producer mid-session in a live browser tab while watching the console — a static code read looked fine.

Fix, two layers

(1) The state poller now caches the last-known-good state and merges fresh data on top of that cache instead of {}. (2) IngestionStep.tsx got defensive fallbacks, and every step is now wrapped in a small ErrorBoundary keyed by the current step.

#3 /api/anomalies risks READ_TOO_MANY_TOMBSTONES as data grows — not fixed, flagged
Symptom

Cross-checking an anomaly row via cqlsh with the same ALLOW FILTERING shape (no bucket_start) failed outright with ReadFailure: ... READ_TOO_MANY_TOMBSTONES; the same shape narrowed to one partition succeeded but logged a tombstone warning (~6,800 tombstone cells alongside ~7,150 live rows in one 15-minute bucket).

Likely cause (not confirmed further)

The spark-cassandra-connector writes NULL row fields as per-column tombstones by default; raw_events has several usually-null columns (anomaly_reason on ~95% of non-anomalous rows), so tombstones accumulate quickly with no TTL/compaction pressure to clear them.

Why not fixed now

/api/anomalies reuses the exact CQL shape already provisioned for the P4 Grafana panel, scoped by since_minutes/LIMIT so it stayed under the failure threshold in this session's testing — but the underlying risk grows with data volume, not with anything P5 added. A real fix is a P3/Cassandra-schema-level change.

General P5 lesson: both real bugs (#1 and #2) were invisible from reading the code or the JSON contract alone — they only showed up when actually watching live REPLAY-mode traffic and actually killing a container mid-session in a real browser tab.

producer restarts forever with FileNotFoundError: /data/iot_telemetry_data.csv, immediately after startup.

The Kaggle dataset isn't committed (~62 MB, gitignored) and the only way to get it in place was a manual host-side step, easy to skip on a fresh VPS clone. P8 — Role-based redirect (Loki/Promtail, alerting, planner map)

2 incidents
#1 loki never reaches healthy, which blocks promtail from starting at all
Symptom

On the first real deploy after adding Loki, loki stuck at Up ... (unhealthy) indefinitely, and promtail never started — the overall docker compose up -d command exited non-zero.

Cause

The healthcheck (wget --spider http://localhost:3100/ready) assumed the same tooling the Prometheus/exporter images ship with. The official grafana/loki image does not: docker compose exec loki sh returns exec: "sh": executable file not found — this image ships nothing but the loki binary and CA certs. A CMD-SHELL healthcheck can never work against it, regardless of which tool it tries to invoke.

How it was found

Live-verified against a real docker compose up — logs showed Loki itself starting and serving real queries successfully, ruling out an application-level failure and pointing at the healthcheck mechanism itself.

Fix

Removed the healthcheck: block from loki entirely, and changed promtail's dependency from service_healthy to service_started — Promtail already retries its own push requests.

General lesson

Don't assume a Docker Hub image includes the same debugging toolbox as unrelated images already in the stack, even official ones from the same vendor. Verify what's actually executable inside a new image before picking a healthcheck strategy.

P9 — Several containers stuck Exited for days

1 incident
Incident spark-job, kafka-ui, promtail, kafka-exporter stuck Exited for days
Symptom

docker compose ps -a showed four restart: unless-stopped services sitting in Exited — no crash loop visible, everything else in the stack up and healthy. Looked at first like the compose file had no real startup ordering.

Cause, two parts

(1) spark-job holds a long-lived Cassandra driver session. Earlier in the same session, a scoped up -d --build backend had cascaded into recreating cassandra too (its own dependency chain touched it), giving it a new container IP mid-stream — spark-job couldn't recover the in-flight queries. restart: unless-stopped did keep bringing it back (RestartCount: 9), but eventually landed back in Exited with nothing prompting a 10th attempt. (2) The four dead services shared one thing: none were named in any follow-up docker compose up -d --build <service> — every command that session scoped to backend only. Compose's up only reconciles the service(s) you name; it does not sweep the rest of the project back to its desired state.

How it was found

docker inspect ... OOMKilled ruled out a memory kill on all four; FinishedAt timestamps clustered within ~2 seconds, pointing at one shared external event. RestartCount: 9 (not 0) proved the restart policy was working, narrowing the question from "why doesn't restart work" to "why did reconciliation stop being attempted."

Fix

docker compose up -d --wait — no service argument, the whole project. Compose recomputes the full dependency graph and brings every drifted service back in correct order in one shot; --wait blocks until every healthchecked service actually reports healthy.

General lesson

The compose file's depends_on/condition: graph was never missing — what causes a "half the stack is dead" scare is scoping up to one service during iterative work and never following up with a bare, whole-project docker compose up -d --wait to reconcile stragglers. Run it after any targeted rebuild, and after anything that might have interrupted Docker Desktop itself (host sleep/resume, a WSL2 restart, a Docker Desktop update).

P10 — spark-job executor OOM-killed catching up on a Kafka backlog (VPS)

1 incident
Incident Executor OOM-killed catching up a Kafka backlog
Symptom

On a public VPS, spark-job was found mid-restart-loop while the producer kept publishing the whole time. Logs showed Lost executor 2 ... Command exited with code 137, followed by a cascade of FetchFailed/MetadataFetchFailedException errors as the driver discovered the dead executor's shuffle outputs were gone — that cascade eventually took the whole streaming query, and then the driver container itself, down.

Cause

read_kafka() had no maxOffsetsPerTrigger cap, so each 30-second trigger pulled as much Kafka backlog as existed, with no ceiling. Since the producer never stops publishing even while spark-job is down, any prior interruption leaves a backlog that grows for as long as the outage lasted — the next catch-up trigger then tries to process the entire backlog in one oversized batch. spark-worker's mem_limit (1500m at the time) couldn't absorb the spike, so Docker's cgroup OOM-killed the executor process. Once killed, the query retries the batch — pulling the same, now-even-larger backlog again: a self-reinforcing loop.

How it was found

Live-diagnosed over SSH against the real VPS. docker inspect ... RestartCount proved the container was self-healing (narrowing the question) before docker compose logs surfaced the actual exit-code-137 executor loss. free -h ruled out host-wide memory exhaustion. docker stats --no-stream then showed spark-worker at 376% CPU and double-digit-GB I/O immediately after the restart — the signature of a backlog catch-up burst, which is what pointed at the missing maxOffsetsPerTrigger.

Fix, three changes together

(1) read_kafka() now sets maxOffsetsPerTrigger (new SPARK_JOB_MAX_OFFSETS_PER_TRIGGER env var, default 20000) — the actual root fix, bounding every micro-batch regardless of backlog size. (2) spark-worker's mem_limit raised 1500m → 2560m, spark-job's 1500m → 2000m — headroom for three independent applyInPandasWithState queries each spawning their own Python subprocess on top of the JVM heap. (3) Confirmed the deployment guide's VPS sizing table already flags this: "sustained 100 msg/s, indefinitely" calls for 16 GB RAM, not the 8 GB "demo only" tier — the observed 11 GB box sat between the two.

General lesson

A Structured Streaming source with startingOffsets: earliest and no per-trigger cap is only safe as long as the query never falls behind for long. Any Kafka source meant to run unattended for an indefinite demo needs an explicit backlog cap from the start, not just tuned container memory limits after the first incident.

P11 — Deploying the P10 fix itself failed: kafka-volume-init raced a live Kafka

1 incident
Incident kafka-volume-init raced a live, running Kafka on the same volume
Symptom

Running docker compose up -d --build spark-job spark-worker --wait to deploy the P10 fix — a command that should only have touched two services — instead cascaded into kafka-volume-init failing with exit 1, which blocked kafka from starting, which in turn stalled cassandra and everything behind it.

Cause

chown: /var/lib/kafka/kafka_data/replication-offset-checkpoint.tmp: No such file or directory. kafka-volume-init's command was an unconditional chown -R, every single time it runs — and docker compose up, even scoped to unrelated services, still re-runs every already-Exited one-shot init container (the same behavior as P9). Here it re-ran while the already-running, healthy kafka container was actively renaming its own checkpoint files in that same shared volume — a straightforward TOCTOU race: chown -R found the .tmp file while walking the tree, then it was gone (renamed over the real file, Kafka's normal checkpoint-write pattern) by the time chown tried to touch it.

How it was found

df -h on the VPS first ruled out disk-full (174 GB free of 193 GB), which narrowed it to the exit-1 log line itself — the specific .tmp filename immediately pointed at a live-file race rather than a permissions or missing-directory problem.

Fix

Both kafka-volume-init and spark-job-volume-init now check the target directory's current owner first and only run the recursive chown if it doesn't already match: [ "$(stat -c '%u' <dir>)" = "<uid>" ] || chown -R <uid>:<gid> <dir>. After the genuine first-ever init of a fresh volume, every subsequent docker compose up now short-circuits before touching the directory at all.

General lesson

An unconditional chown -R in a one-shot init container is only actually safe on the container's first run against a fresh volume — restart: "no" only stops automatic restarts, not Compose re-invoking it deliberately later. Any init command that mutates a volume another, possibly-still-running service also owns needs to be idempotent and cheap to re-check, not just idempotent in its end state.
