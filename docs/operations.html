Resuming locally

docker compose up -d --wait

Brings up the full stack — the producer starts automatically and immediately begins replaying the Kaggle dataset at 100 msg/s into topic sensor-readings, and the Spark job starts consuming and writing to Cassandra right after. Grafana auto-provisions both datasources and the KPI dashboard with zero manual steps. See the root README.md for the verification checklist.

Always use this bare, whole-project form (no service name) to resume/reconcile — a scoped docker compose up -d --build <service> only touches that one service and leaves any sibling that had drifted to Exited (host sleep, a Docker Desktop restart, a crash loop) dead until something names it again (P9).

If you edit infra/prometheus/prometheus.yml while the stack is already running, docker compose restart prometheus is required — it does not hot-reload scrape config from a running container.

Heads up on cold start: on first launch (or after a full down -v), the Spark job recomputes its anomaly-detection baseline from the CSV (~30–60s) before it starts consuming, and if Kafka already has a large backlog, the first micro-batch can take several minutes to catch up — expected, not a hang (see P3).

The Kaggle dataset is fetched automatically by the dataset-init one-shot service into a named volume — no manual step, and a no-op on restarts once the volume has the file (see P6 for the bug this replaced). To fetch it by hand instead, run python kaggle_repository/download_repository.py.

Role scenario walkthroughs (D41)

Added after external review of the v2.0 build noted the use-case list's one-line success criteria didn't add up to a believable "a real user does X, reads Y, reacts Z" story for either role. These two walkthroughs are concrete, narrated, and grounded in the actual UI (D38-D40), not a restatement of REQUIREMENTS.md's UC-10/UC-11.

Planner: is this CO reading normal for this time of year?

It's a warm afternoon. A planner logs in with the planner account and lands on the Lingen (Ems) map. The pin near Kaiserstraße/B70 (b8:27:eb:bf:9d:51) is showing amber — warning, not critical. They click it: the detail panel shows an air quality score of 61, and a provenance label under the status badge reads "Live/synthetic — generated …" — so they know this number is the running pipeline's own reading, not a replayed historical one.

They open the CO chart below the map and tick "Compare to an earlier period." The per-day chart overlays a dashed line labeled "compare (1 week ago, live)" — CO was similar a week ago, so this isn't a new pattern. Curious whether this is just how this spot behaves in general, they check the per-month chart: its compare overlay is labeled "compare (1 year ago, dataset)" instead of live — the deployment hasn't been running for a year, so the backend fell back to the Dataset Explorer's real 2020 data for that device automatically, and says so on the label rather than silently returning nothing or, worse, a fabricated number.

Wanting to see the source data itself, they open Dataset Explorer from the header, pick the same device, and see its real collection window (7 days, 2020) and a genuine sample of readings, each timestamped to when it was actually collected — not event_ts. They now have an answer to both halves of the brief's question: this reading is elevated but not new, and the underlying device has always run a bit hot on CO relative to the other two — exactly what its placement rationale (§5.6) predicted.

Admin: the disk-usage-critical alert fires

Mid-endurance-run, a critical alert appears in the admin's Alerts tab: "A scraped filesystem is above 85% used." The admin clicks through to Grafana Explore, pre-scoped to the flagged service, and confirms from the KPI-4 disk-growth panel that cassandra_storage_load_count has been climbing linearly all run, as expected under NFR-4's no-TTL retention — not a leak, just the endurance run doing exactly what it's supposed to.

Back in the admin console, they scroll to "Disk capacity — archive & trim" under the Alerts tab and click "Archive oldest data…". A confirmation panel explains this is irreversible against the live store before they can proceed — they confirm. A few seconds later the result line reads: "Archived 214,880 rows across 96 partitions (cutoff 2026-09-10T03:00:00.000Z) to /archive/archive-20260916T140212123456.ndjson."

Disk usage drops back under the threshold within the next Prometheus scrape interval and the alert clears on its own. The admin hasn't lost the archived data — it's sitting on disk as plain newline-delimited JSON, in the same shape as the live event schema, readable without any special tooling if it's ever needed again — just no longer competing for space with the live write path. NFR-4's "keep everything" is unchanged as the default; this was the one explicit, logged exception to it (D40).

Admin: adding Cassandra storage capacity (D42, UC-12)

On the Cassandra step, the admin sees a per-node storage bar climbing toward its configured budget. They click "Deploy new Cassandra node…", confirm the warning that this starts a real second container, and watch an animated four-step progress view: creating the container, waiting for it to report healthy, waiting for it to join the ring (nodetool status shows it as UN), then done — each step lighting up in turn rather than a static "please wait." A visible notice on this control says plainly that this is a real action, not a simulation: it scales the actual Cassandra StatefulSet through a narrowly-scoped Kubernetes RBAC Role (NFR-16), creating a real pod with its own 5 GiB volume, and there is no matching "remove a node" button — taking a node back out is a manual operator step (D51; the original D42 notice called it a demo convenience).

Once joined, the second node appears in the Deployment step's health grid automatically, and the storage control now shows two bars instead of one. Token ranges rebalance on bootstrap regardless of replication factor (RF stays at 1 for local dev), so the original node's own Storage_Load starts falling — but only once the admin runs docker exec <container> nodetool cleanup by hand: reclaiming the now-unowned disk space is a deliberate manual follow-up (FR-N4), not something the deploy action does on its own.

Known limitation, live-verified: on a modestly-sized host, this can fail. A real second Cassandra JVM's bootstrap-streaming burst is memory-hungry, and the Docker Desktop VM itself — not just the new container's own mem_limit — can simply run out of RAM to give it (confirmed on one dev machine: a 7.7 GiB total VM with ~6.6 GiB already committed to the rest of this ~15-container stack before the second node even starts). When that happens the new container is OOMKilled, the animation correctly shows exactly which step failed with a message naming the cause, and — because it was starving the whole VM, not just its own cgroup — the primary Cassandra node and even unrelated services (spark-job) can briefly restart too before everything self-heals via their own health checks. This is a genuine capacity limit of the host, not a bug in the deploy action: raising the new node's own memory limit does not help when the VM has no free memory left to give at all. The fix, if you hit this, is increasing Docker Desktop's memory allocation (Settings → Resources, or .wslconfig's memory= on Windows) before retrying, not tuning anything in this project's own config.

Implementation decisions beyond the spec

REQUIREMENTS.md is frozen and deliberately doesn't cover implementation details. These were decided while building and matter for anything downstream that touches the same surfaces.

Kafka / Cassandra (P1)

  • Compose project is named iu-sensor-pipeline and no service sets an explicit container_name: — namespaces every container to avoid clashing with unrelated Docker projects on a shared dev machine (P1 §3).
  • Kafka's actual KRaft log directory had to be pinned via KAFKA_LOG_DIRS to match the mounted volume (P1 §2) — do not drop that env var without re-verifying persistence across a real down && up -d cycle.
  • raw_events is partitioned by (device_id, bucket_start) where bucket_start is a 15-minute bucket, sized for the NFR-2 endurance rate. agg_1m / agg_1h are partitioned by (device_id, day) / (device_id, month).
  • The raw_events table has a few columns beyond the literal §5.2 field list: write_ts (Spark sink write time, feeds KPI-2), is_synthetic, is_anomaly, anomaly_reason. The producer only ever populates is_synthetic — the rest are Spark-job-owned.
  • Grafana gets no default credential — GF_SECURITY_ADMIN_PASSWORD is required with no fallback.

Producer (P2) — the wire contract P3 must consume

  • Kafka message value is JSON with exactly: event_id, device_id, event_ts, ingest_ts, co, humidity, lpg, smoke, temp, light, motion, pressure, is_synthetic. No is_anomaly/anomaly_reason/write_ts/bucket_start — those are Spark/Cassandra-sink-owned.
  • event_ts/ingest_ts are ISO-8601 UTC strings with millisecond precision, e.g. "2026-08-18T10:00:00.000Z" — not epoch millis, so Spark's to_timestamp() parses natively.
  • Kafka message key = device_id (UTF-8) — matches FR-K1's partitioning intent.
  • The producer runs always-on with plain docker compose up -d (no profiles: gating) — every restart re-starts ingestion from the beginning of the CSV unless PRODUCER_REPLAY_ROW_LIMIT is set.
  • Producer state is exposed at GET http://localhost:${PRODUCER_STATE_PORT}/state — read-only telemetry (FR-I4), not a control surface. UC-7 (UI control panel) remains an explicitly later phase.
  • Anomaly injection (synthetic mode only) can spike multiple metrics per event simultaneously (weighted 1/2/3 metrics: 70/25/5%), each offset by PRODUCER_ANOMALY_SIGMA_MULTIPLIER (default 4.0, deliberately above §5.4's 3σ threshold to survive baseline drift). P3's detector expects this.

Spark job (P3)

  • Anomaly detection uses an adaptive EWMA per (device, metric) — not a static one-time baseline — seeded from a batch read of the CSV at startup, then continuously updated (decay SPARK_JOB_ANOMALY_EWMA_ALPHA, default 0.001, ≈ 2000-event/12–60s effective window). Checked before updating with the current event's own value.
  • A separate static per-device absolute ceiling exists for co/smoke/lpg only (max(observed_max, p999) × 1.5). temp/humidity rely on the sigma rule alone.
  • anomaly_reason is a semicolon-joined metric:kind(detail) string and can reflect multiple simultaneously-triggering metrics on one event. Confirmed working for both real historical-data outliers during replay and injected synthetic anomalies.
  • Three fully independent Structured Streaming queries (raw_events, agg_1m, agg_1h), each with its own Kafka read and own checkpoint (state-store data is written by executors — P3 §5).
  • write_ts exists only on raw_events — do not add it to agg_1m/agg_1h writes, their schemas don't have that column (P3 §8).
  • FR-S4: same pattern as the producer — a stdlib HTTP /state endpoint fed by a custom StreamingQueryListener (Spark's own REST API on :4040 doesn't expose Structured Streaming query progress).
  • spark-worker builds a custom image instead of pulling apache/spark:3.5.9 directly, and mounts both the dataset and checkpoint volumes — required because executors run there, not the driver (P3, entirely about this driver/executor distinction).

Observability (P4) — wire contract for P5

  • Producer and Spark job both gained GET /metrics (hand-formatted Prometheus text, no prometheus_client dependency) alongside /state — same port, same HTTP server.
  • KPI-1 lag is genuinely 3 separate numbers — the three queries are independent Kafka consumers (Structured Streaming doesn't use classic consumer-group offsets); lag is broker offset minus Spark's self-reported offset, by query — don't collapse to one number.
  • KPI-2 latency is a per-micro-batch snapshot (p50/p95/max of write_ts − event_ts, plus a hop breakdown), computed only where all 3 timestamps exist on one row (raw_events). Refreshed every trigger interval, not a true cross-batch streaming quantile.
  • Grafana needs two datasources — Prometheus (KPI-1/2/4) and a baked-in Cassandra plugin (KPI-3/5), installed at a path outside the pre-existing grafana_data volume (would otherwise be silently shadowed forever).
  • Cassandra builds a custom image too, baking in a jmx_exporter javaagent. The exporter config is fetched verbatim from jmx_exporter's own official example — if KPI-4 metrics ever need to change, re-diff against upstream rather than guessing MBean names (P4 §12).
  • The dashboard's $device_id variable is a static list (the 3 real device MAC IDs), not CQL-driven — SELECT DISTINCT isn't valid on a partial partition-key column in Cassandra.

Web app (P5)

  • One combined container. backend's Dockerfile is multi-stage: a Node stage builds React, a Python stage serves the built dist/ via StaticFiles at /, alongside /api/* and /ws/*.
  • Auth: two fixed credential pairs (admin/planner, both required env vars, no defaults) plus a hand-rolled HMAC-SHA256-signed session cookie — no session-management dependency, deliberately, since there's no user table.
  • Live updates: WebSocket is primary; the frontend falls back to polling if the socket doesn't open within 3s or drops. The backend's own background loops poll regardless of which transport reaches the browser.
  • Upstream-outage resilience: the state poller caches the last-known-good producer/spark-job state and merges fresh data on top of that cache rather than {} — a transient restart no longer changes the response shape. Added after a real crash was found live (P5 §2) — do not remove this caching without re-verifying survival of a mid-session restart producer.
  • Cassandra "recent rows" bucket selection is event-time-based, not wall-clock — derives which partitions to point-read from real timestamps sampled off Kafka, required because REPLAY-mode event_ts used to be historical (P5 §1).
  • No Docker socket is used for the deployment-status step — every service is probed over its own HTTP/TCP port instead.
  • Known, accepted limitation: /api/anomalies can hit READ_TOO_MANY_TOMBSTONES under high data volume, shared with the P4 Grafana panel it mirrors (P5 §3).

Kubernetes migration (D43) — replacing the Docker socket with RBAC

  • Why this exists: D42's admin-triggered Cassandra node-deploy control (UC-12) needed the backend to reach Docker itself, and the only way to do that from inside a container was mounting /var/run/docker.sock — root-equivalent access to the whole host (NFR-15, R-9), called out at the time as demo-only. D43 replaces that entirely: the backend now authenticates to the Kubernetes API as a backend ServiceAccount bound to a namespaced Role (k8s/base/rbac.yaml) that can only read pod/workload status in the iot-pipeline namespace and scale one specific StatefulSet by name (resourceNames: ["cassandra"]) — nothing else in the cluster, and nothing host-level at all. backend/app/cassandra_nodes.py is a full rewrite around the kubernetes Python client instead of docker; the exposed behavior (storage summary, node-deploy animation, its step names) is unchanged.
  • Graceful degradation: if the backend can't load an in-cluster Kubernetes config (e.g. it's actually running under the legacy docker-compose.yml, which has no ServiceAccount to mount), the Cassandra storage/node-deploy endpoints and the new GET /api/admin/kubernetes/status endpoint return 503 instead of crashing the app — surfaced in the frontend as a plain "Kubernetes API not available" message on both the Cassandra step's storage control and the new Kubernetes tab, not a broken page.
  • Workload mapping (full table in REQUIREMENTS.md §4.4): cassandra/kafka became StatefulSets (stable per-replica identity + PVC via volumeClaimTemplates); everything else long-running became a single-replica Deployment; node-exporter/promtail became DaemonSets (genuinely per-node); the three *-volume-init chown containers (P1 §2, P11 §1) were dropped entirely — securityContext.fsGroup on each pod replaces them, matching each image's already-documented default UID (999 cassandra / 1000 kafka+backend / 185 spark, per the original chown targets).
  • Job-completion ordering is a known simplification versus Compose. Kubernetes Jobs don't block downstream pod scheduling the way depends_on: condition: service_completed_successfully did. Deployments that depend directly on another Service being reachable (kafka, cassandra, spark-master) get a plain busybox initContainer TCP-wait loop; nothing does an in-cluster wait for the one-shot Jobs (kafka-topic-init, cassandra-schema-init) actually completing — k8s/local-up.sh does a best-effort kubectl wait --for=condition=complete on them after applying, for operator feedback, not as a hard release gate. This relies on the same client-side retry behavior the Compose-era services already had (cassandra-schema-init's own 30×5s cqlsh retry loop, in particular) rather than a stricter Kubernetes-native guarantee — a real gap versus Compose, left as a P11 follow-up rather than solved here (e.g. a proper Job-aware initContainer, or moving to Helm/Argo hooks — both explicitly deferred by D43).
  • kustomize's built-in loader refuses to reference a file outside the kustomization root as a security restriction — confirmed the hard way running kubectl kustomize k8s/base against ../../infra/... paths (kubectl apply -k enforces the same restriction, with no --load-restrictor escape hatch the way the standalone kustomize CLI has). k8s/base/kustomization.yaml's configMapGenerator entries instead read from a gitignored k8s/base/generated/ that k8s/local-up.sh populates from the real infra/ source files before every apply — infra/ stays the one committed source of truth, generated/ is never committed.
  • Only backend and grafana are exposed to the host (both type: LoadBalancer Services, matched by -p 8000:8000@loadbalancer -p 3000:3000@loadbalancer at k3d cluster create time) — a deliberate narrowing versus Compose, which also published kafka-ui/Prometheus/the Spark UIs/etc. to host ports for dev convenience. Reach those via kubectl -n iot-pipeline port-forward instead.
  • D43 is live-verified, not just statically checked — a full k8s/local-up.sh run on a real k3d cluster, with kubectl -n iot-pipeline get pods confirming every workload 1/1 Running/ Completed and the app exercised end to end in the browser (live row counts flowing through the Pipeline Console, the new Kubernetes status panel reading real pod health). Five real bugs only a live control plane could surface, all fixed:
    1. k8s/local-up.sh's Secret-generation step used to source .env directly — breaks on this project's own pre-existing space-containing values (SPARK_JOB_TRIGGER_INTERVAL=30 seconds, valid for Compose's env-file parser, not for bash). Now extracts just the needed keys with grep/ cut.
    2. Kubernetes auto-injects a <SERVICE>_PORT env var per Service into every pod in the namespace; it collided with Spark's own SPARK_MASTER_PORT and crashed spark-master with a NumberFormatException on the injected tcp://<clusterIP>:7077 value. Fixed with enableServiceLinks: false cluster-wide.
    3. The default RollingUpdate strategy let two Structured Streaming driver generations run at once during a deploy, both competing for the single spark-worker's fixed memory — the second driver's executor kept getting killed and relaunched in a loop, deadlocking the rollout. Switched spark-master/spark-worker/spark-job to Recreate.
    4. Spark's driver advertised its own bare pod hostname to executors — unlike a Compose container name, a plain Deployment pod has no DNS record for its own hostname in Kubernetes, so the executor got UnknownHostException trying to dial back and register. Fixed via SPARK_LOCAL_IP (Downward API status.podIP) plumbed through to spark.driver.host in spark_job/entrypoint.sh (required rebuilding and re-importing the spark-job image).
    Also found: spark-worker was the one component missing its own Service, so the backend's health check to it always failed — added k8s/base/deployment-spark-worker.yaml's Service.
  • Fifth bug, found after a longer live run: Kafka's readiness/liveness probes ran kafka-broker-api-versions.sh — the full Kafka CLI tool, which launches a brand-new JVM on every single invocation — every 10s, for both probes independently. On a CPU/memory-constrained single-node k3d host already running Cassandra/Spark JVMs alongside it, that extra JVM launch routinely missed its own 10s timeout, so Kubernetes killed an otherwise-healthy broker and it never got a long enough uninterrupted run to stabilize — a self-inflicted CrashLoopBackOff from the probes themselves, not a real Kafka failure, which then cascaded into backend/spark-job/ kafka-exporter all crash-looping on KafkaException: ... Broker transport failure (they depend on Kafka being reachable at startup). Fixed by switching both probes to a plain tcpSocket: 19092 check — instant, no JVM spawn, and matches what every other pod's own wait-for-deps initContainer already uses to decide "is Kafka up" (nc -z kafka 19092), so this keeps the same readiness semantics project-wide without the resource cost. statefulset-cassandra.yaml's cqlsh-exec-based probes are the same class of risk (a Python CLI launch instead of a JVM one, lighter but not free) and haven't caused a real failure yet — worth the same fix if one shows up under sustained load.

Cassandra horizontal-scale-out, actually verified end-to-end (D44)

  • Why this exists: the whole reason D42/D43 exist is FR-N2/UC-12 — an admin, watching Cassandra's storage climb toward its budget, clicks a button and a new Cassandra node joins the ring. That specific end-to-end path had never actually succeeded: D42's Docker-socket version OOM-killed a second Cassandra JVM on a 7.7 GiB Docker Desktop VM before completing; D43 verified the Kubernetes plumbing structurally on k3d but didn't re-confirm this exact scenario. Installed real k3s on one of the project's actual Contabo VPS and ran it for real.
  • Bug 1 — RBAC, pods/exec: the Role's create grant (the documented convention) wasn't enough; this real k3s (v1.36.4+k3s1) authorizes the exec-connect call against get instead. nodetool status/exec-backed endpoints (GET /api/admin/cassandra/storage) 403'd until both verbs were granted.
  • Bug 2 — the real one, CASSANDRA_SEEDS was never set: k8s/base/statefulset-cassandra.yaml had no CASSANDRA_SEEDS, so the official Cassandra image's entrypoint defaulted it to each pod's own address. The scaled-out cassandra-1 came up 1/1 Ready — passed its own local cqlsh readiness probe — while actually bootstrapping as a completely separate single-node cluster: its own fresh system_auth superuser role, its own Host ID, and nodetool status on either pod showing only itself. A green pod, zero ring capacity added — the exact failure mode this feature exists to prevent, and one that k3d's own live-verification in D43 didn't happen to catch (that run never actually scaled Cassandra past 1 replica). Fixed with CASSANDRA_SEEDS: cassandra-0.cassandra.iot-pipeline.svc.cluster.local on every replica.
  • Bug 3 — RBAC, pods/status: cassandra_nodes.py's own readiness-wait (_wait_pod_ready_sync) polls read_namespaced_pod_status, a distinct RBAC resource from plain pods. Even with bugs 1 and 2 fixed and the real scale-up/ring-join genuinely succeeding underneath, the admin feature's own orchestration 403'd on this call every time and reported failure over the WebSocket. Fixed by granting pods/status get.
  • Verified clean after all three fixes: POST /api/admin/cassandra/nodes against a fresh single-node cluster ran creating → healthy → joining_ring → done with no manual steps — cassandra-1 bootstrap-streamed real data, both nodes reached nodetool status UN with the ring split ~49/51%, and the storage-summary endpoint correctly reported both nodes' load.
  • Resource contention, again, this time on real hardware: running the whole stack plus a second Cassandra node pushed this 11 GiB VPS to ~200 MiB available memory, OOMKilled the unrelated backend pod, and cascaded into a py4j connection failure in spark-job. Both self-recovered via Kubernetes' normal pod restart with no data loss — but it reconfirms D42's original finding wasn't a Docker-Desktop-only artifact; a second Cassandra node has a real memory cost worth sizing for explicitly in full P6 (NFR-12).
  • Operational note, not a product bug: FR-N2 only ever scales up — D42 deliberately left decommissioning as a manual step. Removing a test node by deleting its pod/PVC directly (rather than nodetool removenode first) leaves the ring believing that node still owns half the token range. Hit this firsthand resetting state between test runs; worth knowing before repeating.

Simulating an approaching storage budget, a 3-node scale-out, and a real concurrency bug (D45)

  • Why this exists: D44 validated the deploy mechanism by calling POST /api/admin/cassandra/nodes directly against a healthy cluster — it never confirmed the actual UC-12 story, where an admin first sees a node genuinely approaching its configured budget in the UI, then deploys. Nothing had ever driven Storage_Load anywhere near CASSANDRA_NODE_STORAGE_BUDGET_BYTES (2 GiB default), and Docker/host-level storage quotas aren't available (§5.8), so there was no obvious way to make a node look "full" for a demo.
  • The budget is just an env var — no code needed to simulate it: lowering CASSANDRA_NODE_STORAGE_BUDGET_BYTES (read once at backend startup, compared against Cassandra's real Storage_Load in storage_summary_sync) below a node's actual current load reproduces the "critical" admin-UI state immediately, with zero code changes — just a temporary override on the live Deployment (kubectl set env deployment/backend CASSANDRA_NODE_STORAGE_BUDGET_BYTES=...), reverted afterward so the committed 2 GiB default (k8s/base/config.env) never changes.
  • Storage_Load lags real writes until a memtable flush: with ~40k rows already written to raw_events (confirmed via cqlsh COUNT(*)) and spark-job actively writing ~3,000 rows/batch, nodetool status's Load stayed flat at the node's tiny post-bootstrap baseline (94.77 KiB) for several minutes — it only reflects on-disk SSTables, not memtables/commitlog. A manual nodetool flush made the real ~2.4 MiB of written data show up immediately. Anything that demos or tests this control needs to account for this lag (flush manually, or wait long enough for Cassandra's own flush thresholds).
  • FR-N4 is visibly real, not just documented: after scaling cassandra-0→cassandra-1, the storage summary showed cassandra-1 at exactly the budget (100%, matching its streamed bootstrap share) while cassandra-0 stayed at 208.8% of the (deliberately tiny) demo budget — new writes rebalance across the ring immediately, but a node's existing data stays put until an admin runs nodetool cleanup (FR-N4, explicitly a manual step, not automated). A real admin using this feature to relieve pressure would still see the original node over budget immediately after "fixing" it — worth knowing going in, not a bug.
  • 3-node scale-out verified for the first time — the memory-contention finding was resource pressure, not a capacity ceiling: D42 and D44 both found a second Cassandra JVM causing OOM pressure, but neither tried a third node. With spark-worker/spark-job and the observability stack (grafana/loki/kafka-ui/kafka-exporter) scaled to 0 first (freeing ~4 GiB on the same 11 GiB VPS), cassandra-1→cassandra-2 completed cleanly — ring-joined within ~2 minutes, ownership rebalanced to a near-even 35.7% / 31.6% / 32.7% split, no OOM, no restarts, memory held at ~3 GiB free throughout. The earlier OOMs were this VPS running everything at once with no headroom, not a hard limit on Cassandra node count.
  • Bug found — a real concurrency defect in CassandraNodes, not a simulation artifact: while the above was running, state_poller's periodic discover_extra_nodes_health_sync() (FR-N3, a plain list_namespaced_pod call) intermittently raised WebSocketBadStatusException. Root cause: kubernetes.stream.stream() (used by _exec_sync for nodetool calls) monkey-patches the target ApiClient's .request attribute for the duration of the call (kubernetes/stream/stream.py's _websocket_request) — not thread-safe. CassandraNodes shared one CoreV1Api/ApiClient between exec-based calls (_exec_sync, on a background thread during ring-join polling) and plain REST calls (_list_cassandra_pods, cluster_status_sync, on state_poller's own periodic thread); when both hit the shared client concurrently, the REST call could land mid-patch and get routed through the websocket path too. Fixed with a second, dedicated CoreV1Api instance used only by _exec_sync, so the monkey-patched client is never shared with plain-REST call sites. Verified with 480 concurrent requests (6 threads each hammering /cassandra/storage and /kubernetes/status, 40 requests/thread) — 0 errors after the fix, versus the original transient failure observed live during a real node deploy.
  • The third node is now a standing cost, not a transient one: FR-N2 has no decommission path, so cassandra-2 stays part of this VPS's steady state. With the full stack and observability services scaled back up afterward, available memory settled at 242 MiB free / 1.6 GiB available — tighter than this VPS's baseline before this session. A concrete NFR-12 data point: each admin-deployed Cassandra node is a permanent addition to the memory budget, not a one-time cost during the deploy itself.

k8s/local-up.sh/local-down.sh genuinely live-verified for the first time — a real kubectl/KUBECONFIG bug (D46)

  • Why this exists: the script had carried a header comment since D43 admitting it was "fork-authored, not live-verified... not a successful end-to-end run," and this VPS — despite running the real k3s-based Cassandra work in D44/D45 — had never actually run this script; D44/D45 went straight against the native k3s install instead. Installed k3d and ran it for real, for the first time.
  • The bug — wrong kubectl config, not a k3d problem: the first run failed immediately, kubectl apply hitting a connection-refused error against 127.0.0.1:6443 instead of ever reaching the freshly-created k3d cluster. Root cause: on this host, /usr/local/bin/kubectl is a symlink to the k3s binary itself (its own bundled k3s kubectl convenience subcommand) — a normal outcome of installing k3s via get.k3s.io, and therefore a real risk on any machine that also follows this project's own production-VPS setup (D18). That bundled kubectl defaults to /etc/rancher/k3s/k3s.yaml and silently ignores the standard ~/.kube/config file k3d cluster create correctly merges into, unless KUBECONFIG is explicitly set — so the k3d cluster itself was fine the whole time, but every kubectl call in the script was quietly talking to the wrong (in this case stopped) cluster.

  • Verified the full cycle twice: once reusing an existing cluster after the fix, and once genuinely from scratch — local-down.sh fully destroying the cluster, then local-up.sh recreating it. Both times every pod reached Running/Completed and both host-exposed services responded correctly (backend 200, grafana 302 redirect-to-login).
  • The other "5 bugs" D43 claims were mostly already fixed inline: checked git history against D43's own live-verified narrative — 3 of those 5 (SPARK_MASTER_PORT collision, the Recreate deadlock fix, SPARK_LOCAL_IP via the Downward API) are already correctly present in the current manifests, committed as part of D43 itself rather than left broken. Only 2 became separate follow-up commits (.env comment-stripping, the Kafka probe tcpSocket fix) — both already verified working here too. This KUBECONFIG issue was the only genuinely new, previously-undiscovered bug in this path.

k8s/local-down.sh left orphaned Docker resources on every run (D47)

  • Fix: force-remove the tools container, network, and volume by name after k3d cluster delete returns, each suffixed || true since a clean k3d run may have already removed them. Verified directly: reproduced the stuck resources, ran the fixed script, confirmed all three gone via docker ps/ network ls/volume ls.

k8s/deploy.sh: one deploy mechanism for local and production, and the documentation that didn't match reality (D48)

  • The problem: D43 promised one manifest set for local (k3d) and production (k3s), but only half was built. Local had local-up.sh; production had a hand-typed list of kubectl commands in the README that silently omitted steps local-up.sh performs. docs/deployment.html was never updated after D43 and still called docker compose the production path — while the VPS was in fact running k3s (D44–D47).
  • Fix: k8s/deploy.sh <local|prod> <check|up|update|status|down> — the shared steps once, with each local/prod difference isolated in a commented branch (justified here). local-up.sh/local-down.sh remain as one-line wrappers so existing references keep working.
  • Documentation defects found and fixed while doing it (each was misleading a reader, not just incomplete):
    • .env vs k8s/base/config.env. The README told you to set PRODUCER_RATE_MSGS_PER_SEC/PRODUCER_REPLAY_ROW_LIMIT in .env. On Kubernetes .env is read only for six secrets; those keys live in config.env, so the documented endurance-run and demo-hand-over procedures did nothing. Found live: this VPS's .env had BACKEND_COOKIE_SECURE=true while config.env says false — silently ignored. deploy.sh now warns on any such mismatch.
    • The prod path skipped required steps: staging the gitignored k8s/base/generated/ (without it kubectl apply -k fails on a fresh clone), creating the namespace before the Secret, stripping trailing # comments from .env values, and loading the images into k3s' own containerd (Docker's image store is not visible to k3s).
    • "Picks up a code change automatically, every local-up.sh run" was wrong. Images are tagged :local; re-importing under the same tag isn't a pod-spec change, so kubectl apply leaves the old container running. Code changes need a rollout restart in local and prod alike — now deploy.sh update <service>. (Derived from how Kubernetes decides to replace a pod and from the README's own explanation for the prod path; not separately re-run on k3d.)
    • Stale images: when this was written, k3s' containerd held images built before commit 6e0f87b (backend, spark_job) — a plain re-apply would have redeployed the old code.
    • The compose firewall claim was false. deployment.html said ufw allow rules "close the gap" that Docker's iptables rules open. They don't: Docker's rules are evaluated before ufw's, so every port docker-compose.yml publishes (Kafka, Cassandra, Prometheus, Spark UIs, …) is reachable from the internet regardless. Corrected, with the real mitigation (bind to 127.0.0.1 or use the DOCKER-USER chain).
    • Missing k3s operations guidance: the deployment guide's backups, updates, monitoring, teardown and reboot sections described Docker volumes and docker compose commands. Rewritten for PVCs under /var/lib/rancher/k3s/storage, kubectl, and the :local-image-GC trap (a recreated pod can't pull an image that only ever existed in this host's containerd).
  • Deliberate safety behavior in prod: refuses placeholder or short secrets; down touches only the namespace and needs a typed confirmation; refuses multi-node clusters (images and local-path PVCs are single-host); always uses an explicit kubeconfig (D46). There is no set -x trace mode because it would print the secrets read from .env.
  • Verification status — read this: deploy.sh check (both environments, against the real k3s API), argument handling, the config-validation failure paths and the drift warning were run on the production VPS, and the kubectl/k3s ctr command shapes were confirmed. up, update and production down were not run end to end when this was written: their shared steps are ported unchanged from the live-verified D46/D47 scripts, but the new prod branches (image load via k3s ctr, namespace-only down, the confirmation prompt) are unproven until the first real run. Update this entry with the outcome.

Production hardening after go-live: a poisoned Kafka message and a backend OOM (D49)

  • Provenance: commit 6e0f87b, recorded here retroactively from its commit message (it had no decision-log entry). Its live-verification claims were not re-checked when this was written.
  • Incident 1 — one bad message crash-looped the whole pipeline. A Kafka message that failed JSON parsing, or parsed but lacked event_id/device_id/event_ts/ingest_ts, reached applyInPandasWithState and crashed all three streaming queries with an Arrow null-timestamp error. The checkpoint always resumed at the same offset, so it never self-healed. Fix: spark_job/spark_job/schema.py drops such messages before the stateful stage. Known trade-off: they are dropped silently — there is no dead-letter topic and no alert, so a misbehaving producer would lose events without anyone being told.
  • Incident 2 — the backend was OOM-killed by "compare to an earlier period". That toggle fires up to three Dataset Explorer queries at once (day/week/month), and each re-scanned the whole Kaggle CSV; three concurrent full scans exceeded the pod's memory. Fix: backend/app/dataset_reader.py parses the CSV once and caches it; the backend limit went 384Mi → 512Mi for headroom around the cache.

Memory limits resized to fit the 11 GB production node (D50)

  • Provenance: commit 908c1dd, recorded retroactively from its commit message; not re-verified here.
  • Why: the sum of container limits was ~12.4 GiB across the 14 steady-state workloads — already over the VPS's 11 GB before OS/k3s overhead, matching D44/D45's observation of only ~200 MiB–1.6 GiB free with everything running.
  • What changed: peripheral services (grafana, prometheus, loki, kafka-exporter, producer, node-exporter, promtail) trimmed to observed usage plus margin; spark-job and spark-master moderately trimmed; cassandra, kafka, spark-worker and backend deliberately untouched (each tied to a real OOM/stall incident). New totals ≈ 9.6 GiB limits, ≈ 4.8 GiB requests, ≈ 5.5 GiB real usage.
  • kafka-ui is now off by default (0 replicas). Turn it on with kubectl -n iot-pipeline scale deployment kafka-ui --replicas=1; a later deploy.sh up resets it to 0 because the manifest declares 0.
  • A subtle coupling: shrinking spark-master's limit also required setting SPARK_DAEMON_MEMORY. Spark daemons default to a 1 GiB heap regardless of the container limit, so lowering the limit alone would have made it self-OOM on every start.
  • Consequence to remember: only ~1.4 GiB sits between the limit total and the host's RAM. Anything that adds a pod, raises a limit or scales Cassandra must re-check kubectl top nodes first.

Troubleshooting log

Non-obvious bugs, gotchas, and environment quirks — ordered by phase. Kept so a future debugging session doesn't rediscover the same root cause from scratch.

P1 — Foundation (local docker-compose stack)

3 incidents
#1 Cassandra crash-loops on boot: unable to find snitch class
Symptom

cassandra exits immediately (exit code 3) on every start; docker compose logs cassandra shows ConfigurationException: Unable to find snitch class 'org.apache.cassandra.locator.GossipPropertyFileSnitch'.

Cause

Typo. The real class is GossipingPropertyFileSnitch (with "-ing") — there is no GossipPropertyFileSnitch in Cassandra.

Fix

CASSANDRA_ENDPOINT_SNITCH: GossipingPropertyFileSnitch in docker-compose.yml.

#2 Kafka data silently does not survive a restart (breaks NFR-8)
Symptom

No error at all — the stack looks healthy after every restart. But the topic's TopicId is different every time, meaning the whole KRaft cluster was silently recreated from scratch.

Cause

The volume was mounted at /var/lib/kafka/kafka_data, but the apache/kafka:3.7.0 image's actual KRaft log directory is /tmp/kafka-logs — visible only in the JVM's own runtime log line, not in the config file that looks effective but is just a template. The mounted volume was therefore never actually written to.

How it was found

Inserted a probe row / recorded a TopicId, ran a real down + up -d cycle, and diffed before/after — config validation alone does not catch this class of bug.

Fix

Two parts: (1) KAFKA_LOG_DIRS: /var/lib/kafka/kafka_data explicitly set. (2) A new one-shot kafka-volume-init service (runs as root, chowns the volume) that kafka depends on via service_completed_successfully — needed because a fresh named volume mounts root-owned by default, but the image runs as non-root uid 1000.

General lesson

Don't trust a config file found via find/cat inside an image to be the effective runtime config — confirm the actual data directory from the process's own startup log, and confirm persistence by actually cycling the stack and diffing an identifier, not just checking the container starts.

#3 Host port / container-name collisions are with unrelated things on this machine
Symptom & cause

kafka-ui's default host port 8080 collided with an unrelated pre-existing process on this dev machine — worked around by remapping KAFKA_UI_PORT in the local, gitignored .env (deliberately not changed in .env.example). Separately, stopped leftover containers already existed named kafka/kafka-ui/spark-master from unrelated old projects.

Fix

Fixed at the project level, not by touching those containers: added name: iu-sensor-pipeline at the top of docker-compose.yml and removed every explicit container_name: override, so Compose namespaces everything as iu-sensor-pipeline-<service>-1.

General lesson

Don't hardcode container_name: in a compose file meant to run on a shared dev machine — let Compose's project-prefixed default naming do its job.

P3 — Processing (PySpark Structured Streaming job)

5 incidents

The unifying theme of every bug below: this is a real distributed cluster (a spark-job driver container plus a separate spark-worker executor container), not a single-process local Spark session. Anything that "obviously" only needs to exist on the driver can silently fail on the executor instead. Every fix is a variant of "make sure executors have it too, not just the driver."

#4 Batch CSV read fails on the executor: file does not exist
Symptom

The job's one-time baseline-seed read fails with SparkFileNotFoundException, reported by a task running on the worker's IP, not the driver.

Cause

spark.read.csv(...) is a distributed batch read — Spark schedules the actual read task on an executor, not the driver. Only spark-job's compose service had the volume mounted.

Fix

Mount the same volume into spark-worker too.

General lesson

Any local file path a Spark job reads or writes must be mounted identically on every node that can run a task for that job, not just the driver — true even for a single-worker "cluster."

#5 Checkpoint mkdir fails for state-store paths
Symptom

java.io.IOException: mkdir of file:/opt/spark-checkpoints/agg_1m/state/1/0/_metadata failed.

Cause

Two layered issues: a fresh named volume mounts root-owned (same lesson as P1 §2), fixed with a spark-job-volume-init one-shot chown -R 185:185. Less obviously: Structured Streaming's state-store data (for applyInPandasWithState and windowed aggregations) is written by executors, not the driver — so spark_checkpoints also needed mounting into spark-worker.

Fix

Mount spark_checkpoints into both spark-job and spark-worker; chown via spark-job-volume-init before either starts.

#6 ModuleNotFoundError: pandas / pyarrow on the executor
Symptom

The driver starts fine, but the first micro-batch that runs applyInPandasWithState fails on the executor with ModuleNotFoundError, deep in PySpark's Arrow serialization code.

Cause

applyInPandasWithState is a pandas UDF under the hood — needs pandas/pyarrow wherever it actually executes, which is the executor. The base apache/spark:3.5.9 image ships neither; spark_job/Dockerfile correctly installs both, but spark-worker was still using the plain upstream image.

Fix

A new spark_job/worker.Dockerfile (base image + the same requirements.txt), and spark-worker switched from a pulled image: to a build: using it.

General lesson

PySpark auto-distributes --packages JARs to executors, but does not auto-distribute pip-installed Python packages — those need to be baked into whatever image the executors actually run.

#7 ModuleNotFoundError: spark_job, unpickling a closure
Symptom

Different from #6 — this is the job's own package failing to import on the executor while deserializing the applyInPandasWithState function via cloudpickle.loads.

Cause

A wrong assumption: cloudpickle pickles functions defined in an importable module (as opposed to __main__) by reference, not fully "by value" — it expects the receiving side to import it. Since spark_job was never shipped to the executor, unpickling fails there.

Fix

Zip the spark_job/ package at build time and add --py-files /opt/app/spark_job.zip to the spark-submit command.

General lesson

Don't assume PySpark UDF closures are executor-independent just because they're passed as plain Python callables — if the function lives in a real package, ship it via --py-files regardless.

#8 Cassandra connector rejects a write with columns the table doesn't have
Symptom

NoSuchElementException: Columns not found in table iot.agg_1h: write_ts — the connector aborts outright rather than silently dropping the column.

Cause

The shared foreachBatch writer helper unconditionally added a write_ts column to every DataFrame, but only raw_events actually has that column — a window's aggregate has no single meaningful "row write time."

Fix

Made stamp_write_ts a parameter of the writer factory, True only for the raw_events query.

General lesson

A generic "one writer for every table" helper is a trap the moment the tables' schemas actually differ — verify against each target table's real column list.

General P3 lesson: all five bugs above were caught by actually running the job against the live stack — including a stack that already had ~9 hours of real producer traffic queued in Kafka. None would have surfaced from a syntax check or code review alone — they're all specifically about the driver/executor split in a genuine (if small) cluster.

The panel queries used bare $granularity in the FROM clause, while a working variable elsewhere in the same queries used the curly-brace form. The bare form was never substituted — Cassandra's CQL grammar treats a bare $ as the start of a dollar-quoted string literal.

How it was found

P9 — Several containers stuck Exited for days

1 incident
Incident spark-job, kafka-ui, promtail, kafka-exporter stuck Exited for days
Symptom

docker compose ps -a showed four restart: unless-stopped services sitting in Exited — no crash loop visible, everything else in the stack up and healthy. Looked at first like the compose file had no real startup ordering.

Cause, two parts

(1) spark-job holds a long-lived Cassandra driver session. Earlier in the same session, a scoped up -d --build backend had cascaded into recreating cassandra too (its own dependency chain touched it), giving it a new container IP mid-stream — spark-job couldn't recover the in-flight queries. restart: unless-stopped did keep bringing it back (RestartCount: 9), but eventually landed back in Exited with nothing prompting a 10th attempt. (2) The four dead services shared one thing: none were named in any follow-up docker compose up -d --build <service> — every command that session scoped to backend only. How it was found

docker inspect ... OOMKilled ruled out a memory kill on all four; FinishedAt timestamps clustered within ~2 seconds, pointing at one shared external event. RestartCount: 9 (not 0) proved the restart policy was working, narrowing the question from "why doesn't restart work" to "why did reconciliation stop being attempted."

Fix

docker compose up -d --wait — no service argument, the whole project. Compose recomputes the full dependency graph and brings every drifted service back in correct order in one shot; --wait blocks until every healthchecked service actually reports healthy.

General lesson

The compose file's depends_on/condition: graph was never missing — what causes a "half the stack is dead" scare is scoping up to one service during iterative work and never following up with a bare, whole-project docker compose up -d --wait to reconcile stragglers. P10 — spark-job executor OOM-killed catching up on a Kafka backlog (VPS)

1 incident
Incident Executor OOM-killed catching up a Kafka backlog
Symptom

On a public VPS, spark-job was found mid-restart-loop while the producer kept publishing the whole time. Logs showed Lost executor 2 ... Command exited with code 137, followed by a cascade of FetchFailed/MetadataFetchFailedException errors as the driver discovered the dead executor's shuffle outputs were gone — that cascade eventually took the whole streaming query, and then the driver container itself, down.

Cause

read_kafka() had no maxOffsetsPerTrigger cap, so each 30-second trigger pulled as much Kafka backlog as existed, with no ceiling. Since the producer never stops publishing even while spark-job is down, any prior interruption leaves a backlog that grows for as long as the outage lasted — the next catch-up trigger then tries to process the entire backlog in one oversized batch. spark-worker's mem_limit (1500m at the time) couldn't absorb the spike, so Docker's cgroup OOM-killed the executor process. Once killed, the query retries the batch — pulling the same, now-even-larger backlog again: a self-reinforcing loop.

How it was found

Live-diagnosed over SSH against the real VPS. docker inspect ... RestartCount proved the container was self-healing (narrowing the question) before docker compose logs surfaced the actual exit-code-137 executor loss. free -h ruled out host-wide memory exhaustion. docker stats --no-stream then showed spark-worker at 376% CPU and double-digit-GB I/O immediately after the restart — the signature of a backlog catch-up burst, which is what pointed at the missing maxOffsetsPerTrigger.

Fix, three changes together

(1) read_kafka() now sets maxOffsetsPerTrigger (new SPARK_JOB_MAX_OFFSETS_PER_TRIGGER env var, default 20000) — the actual root fix, bounding every micro-batch regardless of backlog size. (2) spark-worker's mem_limit raised 1500m → 2560m, spark-job's 1500m → 2000m — headroom for three independent applyInPandasWithState queries each spawning their own Python subprocess on top of the JVM heap. (3) Confirmed the deployment guide's VPS sizing table already flags this: "sustained 100 msg/s, indefinitely" calls for 16 GB RAM, not the 8 GB "demo only" tier — the observed 11 GB box sat between the two.

General lesson

A Structured Streaming source with startingOffsets: earliest and no per-trigger cap is only safe as long as the query never falls behind for long. Any Kafka source meant to run unattended for an indefinite demo needs an explicit backlog cap from the start, not just tuned container memory limits after the first incident.

P11 — Deploying the P10 fix itself failed: kafka-volume-init raced a live Kafka

1 incident
Incident kafka-volume-init raced a live, running Kafka on the same volume
Symptom

Running docker compose up -d --build spark-job spark-worker --wait to deploy the P10 fix — a command that should only have touched two services — instead cascaded into kafka-volume-init failing with exit 1, which blocked kafka from starting, which in turn stalled cassandra and everything behind it.

Cause

chown: /var/lib/kafka/kafka_data/replication-offset-checkpoint.tmp: No such file or directory. kafka-volume-init's command was an unconditional chown -R, every single time it runs — and docker compose up, even scoped to unrelated services, still re-runs every already-Exited one-shot init container (the same behavior as P9). Here it re-ran while the already-running, healthy kafka container was actively renaming its own checkpoint files in that same shared volume — a straightforward TOCTOU race: chown -R found the .tmp file while walking the tree, then it was gone (renamed over the real file, Kafka's normal checkpoint-write pattern) by the time chown tried to touch it.

How it was found

df -h on the VPS first ruled out disk-full (174 GB free of 193 GB), which narrowed it to the exit-1 log line itself — the specific .tmp filename immediately pointed at a live-file race rather than a permissions or missing-directory problem.

Fix

Both kafka-volume-init and spark-job-volume-init now check the target directory's current owner first and only run the recursive chown if it doesn't already match: [ "$(stat -c '%u' <dir>)" = "<uid>" ] || chown -R <uid>:<gid> <dir>. After the genuine first-ever init of a fresh volume, every subsequent docker compose up now short-circuits before touching the directory at all.

General lesson

An unconditional chown -R in a one-shot init container is only actually safe on the container's first run against a fresh volume — restart: "no" only stops automatic restarts, not Compose re-invoking it deliberately later. Any init command that mutates a volume another, possibly-still-running service also owns needs to be idempotent and cheap to re-check, not just idempotent in its end state.
